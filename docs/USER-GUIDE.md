# Design Intelligence Agent — полное руководство

Агент для исследования, проектирования и проверки интерфейсов мобильных и веб-продуктов.

Он помогает находить актуальные дизайн-референсы, анализировать существующие продукты,
сравнивать UX-паттерны, выявлять хорошие практики и антипаттерны, выбирать подходящее
решение под конкретную задачу и превращать его в структуру экрана, спецификацию или
прототип.

Агент различает mobile, web и cross-platform контексты, учитывает платформу, продуктовый
домен, пользовательскую задачу, технические ограничения и существующую дизайн-систему.

Он может работать в нескольких форматах:

- исследовать широкое пространство идей;
- давать решения, основанные на реальных продуктах и официальных рекомендациях;
- анализировать скриншоты, макеты, код и текущий UX;
- проектировать новые экраны и пользовательские сценарии;
- помогать с редактированием и развитием существующего дизайна;
- готовить решения для реализации в Figma, React Native, Expo, React, Next.js и других
  инструментах.

Агент не просто показывает красивые референсы. Он объясняет, какую задачу решает каждый
паттерн, почему он подходит или не подходит продукту, что можно перенести, а что является
платформенно или контекстно зависимым.

## 1. Для чего нужен агент

Используйте его, когда нужно:

- найти дизайн-референсы под конкретную задачу;
- исследовать возможные направления нового интерфейса;
- выбрать между несколькими UX-паттернами;
- проверить существующий экран или flow;
- найти хорошие практики и антипаттерны;
- адаптировать решение под mobile, web или несколько платформ;
- создать структуру нового экрана;
- улучшить визуальную иерархию;
- спроектировать состояния интерфейса;
- подготовить спецификацию для дизайнера или разработчика;
- превратить выбранное направление в прототип или UI-код;
- проверить готовую реализацию на соответствие исходным решениям.

Агент использует не только знания языковой модели. При необходимости он исследует
актуальные продукты, официальные дизайн-системы, реальные пользовательские сценарии,
отраслевые практики и доступные референсы. Если live-исследование недоступно, агент
обязан честно сообщить об этом (см. раздел 4, Fallback).

## 2. Какие задачи можно ставить

### Поиск референсов

Пример:

> Найди референсы для истории разговоров в мобильном AI-приложении для mental health.
> Основные действия: найти прошлый разговор, понять его тему и продолжить сессию.
> Нужны реальные продуктовые примеры, а не только концепты.

Агент должен: определить платформу и задачу; сформировать несколько направлений поиска;
найти точные и смежные референсы; объяснить применимость каждого решения; отделить
реальные продукты от визуальных концептов; предложить наиболее подходящие паттерны.

### Проектирование нового интерфейса

Пример:

> Спроектируй экран выбора AI-инструмента для мобильного приложения. Инструментов пять,
> пользователь обычно запускает один из них после разговора. Интерфейс должен быть
> спокойным, компактным и не выглядеть как dashboard.

Агент определяет: место экрана в сценарии; информационную архитектуру; основные и
второстепенные действия; способ представления инструментов; необходимые состояния;
визуальное направление; ограничения платформы.

### Аудит существующего дизайна

Можно передать:

- скриншот или несколько экранов;
- Figma-макет;
- описание пользовательского flow;
- **последовательность кадров или скриншотов из записи поведения интерфейса**
  (прямой анализ видеофайлов не поддерживается — извлеките ключевые кадры);
- React Native или web-код;
- существующую дизайн-систему.

Пример:

> Проведи аудит этого экрана. Не переделывай его полностью. Найди реальные проблемы с
> иерархией, навигацией, состояниями и мобильным взаимодействием. Отдели UX-проблемы от
> субъективных визуальных замечаний.

### Сравнение вариантов

> Сравни три варианта навигации: нижние табы, drawer и один chat-first экран без
> постоянной навигации. Продукт — мобильный mental health assistant. Покажи преимущества,
> риски и условия, при которых каждый вариант будет правильным.

### Адаптация между платформами

> У нас есть мобильный экран истории разговоров. Нужно создать web-версию для desktop,
> сохранив продуктовую логику, но не копируя мобильный layout буквально.

Сохраняется: продуктовая модель, терминология, основные задачи, общий визуальный язык.
Адаптируется: навигация, плотность информации, hover и focus states, работа с клавиатурой,
использование пространства, contextual actions, responsive behavior. Для таких задач
существует отдельный режим — cross-platform-synthesis (раздел 4).

### Подготовка к реализации

> На основе выбранного направления подготовь implementation-ready спецификацию для React
> Native и Expo. UI-компоненты должны соответствовать нашей существующей дизайн-системе.

Результат может включать: структуру экранов, component inventory, состояния компонентов,
design tokens, навигационную модель, поведение клавиатуры, жесты, loading/empty/error
states, accessibility, acceptance criteria, рекомендации по реализации.

## 3. Выбор платформы

Контексты: iOS; Android; cross-platform mobile; mobile web; responsive web; desktop web
application; cross-platform product.

Платформу можно указать явно:

```
Platform: cross-platform mobile
Primary target: iOS
Secondary target: Android
Stack: React Native + Expo
```

Или позволить агенту определить её автоматически по запросу, скриншотам, коду и другим
материалам. Агент всегда показывает определённый профиль и уверенность — неверное
определение можно переопределить одной строкой.

Для задач, одновременно затрагивающих web и mobile, используйте режим
**cross-platform-synthesis** (раздел 4). Не следует просить сделать интерфейс «одинаковым
на web и mobile» — правильная формулировка: сохранить общую систему, адаптировав
взаимодействие под каждую платформу.

## 4. Режимы работы

### Explore

Для свободного исследования.

> Explore mode. У меня пока нет конкретного решения. Исследуй разные способы представить
> ежедневную рефлексию в AI-приложении. Можно смотреть соседние категории и предлагать
> необычные направления.

Агент может расширять область поиска, брать референсы из смежных индустрий, создавать
неожиданные комбинации, предлагать экспериментальные решения. Экспериментальные идеи
обязаны иметь метку `derivation: SPECULATION` — это гипотезы, а не общепринятые практики.

### Grounded

Максимальная точность.

> Grounded mode. Используй реальные работающие продукты, официальные рекомендации и
> устоявшиеся паттерны. Не предлагай концептуальные решения без доказательств.

Агент указывает источники; разделяет официальные рекомендации и продуктовые примеры;
объясняет ограничения каждого решения; не выдаёт визуальное предпочтение за UX-правило;
показывает уровень уверенности. В grounded допустимы только `evidenceBasis: LIVE_SOURCE /
REPOSITORY_SOURCE / USER_PROVIDED` с `derivation: DIRECT | SYNTHESIS`.

### Hybrid

Основной рабочий режим.

> Hybrid mode. Сначала найди проверенные паттерны, затем предложи несколько оригинальных
> вариантов, которые остаются реалистичными для реализации.

В результате видно: что взято из реальных решений, что является синтезом нескольких
референсов, что является новой гипотезой агента — через метки evidenceBasis и derivation.

### Audit

Анализ существующего продукта.

> Audit mode. Проверь этот экран на UX-проблемы, платформенные конфликты, accessibility,
> визуальную иерархию и соответствие нашей дизайн-системе.

Находки классифицируются по severity (Standard violation / Platform convention conflict /
Usability risk / Design-system inconsistency / Visual polish / Subjective preference) и по
типу правила (раздел 8).

### Prototype

После выбора направления.

> Prototype mode. Используй выбранный вариант и подготовь структуру интерактивного
> прототипа со всеми основными состояниями.

### Cross-platform synthesis

Отдельный режим для продуктов с mobile- и web-версиями. Это не слияние двух профилей и не
«сделать одинаково»: исследование идёт раздельно по платформам, затем синтез явно
разделяет общее ядро и платформенное поведение.

> Cross-platform synthesis. Одна продуктовая задача — история разговоров. Сохрани общую
> продуктовую модель, терминологию и токены, но предложи платформенно правильную навигацию
> и взаимодействие для mobile и desktop web.

Результат обязан содержать четыре корзины:

```
Stays shared              — продуктовая модель, терминология, токены, визуальная ДНК
Adapts for mobile         — часть → мобильный паттерн
Adapts for web            — часть → веб-паттерн
Must not transfer literally — что сломается при буквальном переносе и почему
```

### Research Sufficiency Gate (перед любым live-поиском)

Агент не ищет по привычке. До live-исследования он принимает и показывает явное решение:

```
researchDecision: reuse-existing | use-user-provided | use-repository-evidence |
                  run-live-quick | run-live-survey | fallback-no-live-research
reason:           почему этого уровня evidence достаточно
freshness:        current | stale | unknown
```

Порядок предпочтения: актуальный прошлый research_summary → переданные вами референсы и
правила → evidence из репозитория (токены, компоненты, аудиты) → live-поиск. Live
запускается только когда нужны свежесть, внешняя проверка или отсутствующие данные.
В режиме prototype с одобренным актуальным направлением ресёрч автоматически не
перезапускается.

### Fallback (не режим, а обязательное поведение)

Если live-исследование недоступно или дало слишком мало результатов, агент обязан:

1. явно сообщить, что live research не выполнен или неполон, и почему;
2. не выдавать внутренние знания модели за результаты поиска — никаких вымышленных
   источников, ссылок и дат;
3. понизить заявленную уверенность;
4. пометить затронутый вывод `evidenceBasis: MODEL_KNOWLEDGE`;
5. перечислить, что требуется проверить позднее.

В grounded-режиме fallback означает честный отказ от grounded-гарантий: агент скажет, что
режим не может быть выполнен без live-источников, и предложит помеченный деградированный
вариант.

## 5. Что полезно передать агенту

Тип продукта; платформа; целевые пользователи; основная задача экрана; место экрана во
flow; существующий интерфейс; дизайн-система; технический стек; ограничения; уже принятые
решения; отклонённые ранее варианты; степень экспериментальности; формат ожидаемого
результата.

Не обязательно заполнять всё — агент работает и с коротким запросом, самостоятельно
формируя рабочие предположения и показывая их явно.

## 6. Рекомендуемый формат запроса

```text
Задача:        что исследовать, проверить или спроектировать.
Платформа:     iOS / Android / cross-platform mobile / responsive web / desktop web.
Продукт:       что это и для кого.
Пользовательская задача: что пользователь должен сделать или понять.
Текущий контекст: как интерфейс устроен сейчас.
Ограничения:   что нельзя менять, какие технологии используются.
Режим:         Explore / Grounded / Hybrid / Audit / Prototype / Cross-platform synthesis.
Результат:     референсы / сравнение / новый экран / спецификация / прототип / код.
```

Пример:

```text
Задача: улучшить экран истории разговоров.
Платформа: cross-platform mobile, iOS primary.
Продукт: mental health AI assistant.
Пользовательская задача: найти прошлую сессию, понять её тему и продолжить разговор.
Текущий контекст: обычный список с названием и датой.
Ограничения: нельзя добавлять постоянный tab bar; React Native + Expo.
Режим: Hybrid.
Результат: референсы, сравнение вариантов, структура экрана и состояния.
```

## 7. Как работать с найденными референсами

Плохой запрос: «Найди много красивых референсов для приложения».

Лучше: «Найди 8–12 релевантных референсов для мобильной истории AI-разговоров. Для каждого
объясни, какую задачу он решает, что можно перенести в наш продукт и что копировать не
стоит».

Каждый референс возвращается с полным контрактом: источник; тип источника; платформа;
продуктовый контекст; решаемая задача; interaction pattern; дата проверки; актуальность;
оценки соответствия; переносимые принципы; ограничения; детали, которые нельзя копировать;
уверенность; evidenceBasis и derivation.

Референс не является готовым решением — он оценивается относительно задачи, платформы и
пользователей.

**Точность значений.** Точная цифра в спецификации допустима только если она измерена,
найдена в источнике, взята из токенов проекта или прозрачно вычислена. Во всех остальных
случаях агент обязан давать диапазон + уверенность + требование валидации — выдуманная
точность считается нарушением контракта.

## 8. Что агент различает

Три независимых словаря, которые не смешиваются.

**Тип источника (sourceType):**

- `official-guideline` — требование платформы или стандарта (HIG, WCAG);
- `official-design-system` — официальная дизайн-система (Material 3, Carbon);
- `real-shipped-product` — реальный работающий продукт: устоявшиеся паттерны и продуктовые
  конвенции живут здесь;
- `case-study-or-research` — исследования и кейсы;
- `concept-or-visual-inspiration` — концепты и визуальное вдохновение. Популярный концепт
  никогда не является доказательством usability.

**Тип правила (при аудите и рекомендациях):**

- `platform rule` — официальное правило платформы или accessibility-стандарта;
- `usability heuristic` — эвристика, проверенная практикой;
- `product convention` — конвенция категории продуктов, не обязательно универсальная;
- `visual preference` — субъективное стилистическое решение; не выдаётся за UX-правило.

**Происхождение вывода (две независимые оси):**

- `evidenceBasis` — на чём основано знание (может быть несколько):
  - `LIVE_SOURCE` — проверено вживую в этой сессии;
  - `REPOSITORY_SOURCE` — прочитано из вашего репозитория;
  - `USER_PROVIDED` — передано вами (правила, референсы, ограничения);
  - `MODEL_KNOWLEDGE` — знания модели; используется в fallback, уверенность понижается.
- `derivation` — как получен вывод:
  - `DIRECT` — взято как есть из основания;
  - `SYNTHESIS` — собрано из нескольких оснований;
  - `SPECULATION` — новая экспериментальная идея, требует прототипирования и проверки.

Оси не сливаются: «SYNTHESIS из трёх live-проверенных паттернов» и «SPECULATION поверх
MODEL_KNOWLEDGE» — разные утверждения, и они читаются по-разному.

## 9. Собственные скиллы, дизайн-система и конфликты

Агенту можно передавать: внутренние design skills; правила продукта; design tokens;
component library; документацию дизайн-системы; предыдущие исследования; принятые
архитектурные решения; скриншоты существующего продукта; примеры хороших и плохих экранов.

> Используй приложенный skill как источник внутренних правил. Не считай все его
> рекомендации универсальными. Сопоставь их с платформой, задачей и найденными реальными
> продуктами.

**Протокол разрешения конфликта.** Внутренняя дизайн-система по умолчанию в приоритете —
но только пока она не создаёт явного usability-, accessibility- или платформенного
конфликта. При конфликте агент обязан показать:

```
1. Внутреннее правило или ограничение дизайн-системы
2. Внешняя рекомендация, evidence или продуктовый паттерн (с evidenceBasis)
3. Область и причина конфликта
4. Влияние каждого из вариантов на пользователя
5. Выбранное решение и обоснование
6. Исключения или платформенно-специфичный override
7. Уверенность и что требуется провалидировать
```

## 10. Что делать не следует

- **Слишком абстрактный запрос без цели.** «Сделай современный дизайн» → лучше:
  «Спроектируй компактный экран выбора инструмента; пользователь должен быстро понять
  разницу между пятью инструментами и запустить один».
- **Слова без определения.** «Современный», «премиальный», «минималистичный», «чистый»,
  «стильный» неоднозначны — описывайте ожидаемое впечатление и ограничения: «спокойный
  интерфейс с низкой визуальной нагрузкой, короткими текстами, выраженной типографической
  иерархией, без dashboard-карточек».
- **Слепое копирование.** «Сделай как Linear» → лучше: «Проанализируй, какие принципы
  Linear применимы к нашему web-продукту: плотность, навигация, command system. Не копируй
  визуальный стиль и проверь применимость каждого принципа».
- **Смешение платформ без необходимости.** «Найди лучшие паттерны навигации» → «Найди
  паттерны навигации для cross-platform mobile; iOS — основная, Android — вторичная».
- **Популярность ≠ качество.** Много похожих экранов на Dribbble не означает, что паттерн
  удобен (Tier D никогда не доказывает usability).
- **Концепты как единственное основание.** Годятся для visual direction, не подтверждают
  usability, accessibility и работоспособность flow.
- **Оценка «хорошо/плохо».** Просите разделять: реальные UX-проблемы; платформенные
  конфликты; несоответствие дизайн-системе; accessibility; визуальный polish; субъективные
  предпочтения.
- **Ранний переход к UI-коду.** Сначала: пользовательская задача, информационная
  архитектура, выбранный паттерн, состояния, ограничения, критерии успеха. Потом прототип
  и реализация (в системе это жёсткий гейт).

## 11. Примеры хороших запросов

- **Свободное исследование:** «Explore mode. Исследуй способы организации главного экрана
  мобильного AI health assistant. Не ограничивайся чат-интерфейсами: посмотри journaling,
  coaching, meditation, productivity. Предложи четыре принципиально разных направления».
- **Точный поиск:** «Grounded mode. Найди реальные реализации conversational onboarding в
  мобильных приложениях. Нужны полные flows, не отдельные экраны. Для каждого — платформа,
  этапы, сильные стороны, ограничения».
- **Аудит:** «Проведи аудит приложенных экранов. React Native, iOS и Android. Проверь
  навигацию, системный back, клавиатуру, safe area, scrolling, loading/empty/error states.
  Не меняй визуальный стиль без необходимости».
- **Web-задача:** «Спроектируй desktop web-интерфейс для истории AI-сессий: поиск, фильтры,
  группировка по времени, быстрый переход к последней сессии. Учитывай keyboard navigation,
  URL-state, responsive behavior и accessibility».
- **Cross-platform:** «Cross-platform synthesis. Сначала общая информационная архитектура,
  затем отдельная navigation model для mobile и desktop web. Не используй одинаковый layout
  на обеих платформах».
- **Спецификация:** «На основе выбранного решения подготовь implementation-ready
  спецификацию: component inventory, состояния, interaction rules, responsive behavior,
  accessibility, acceptance criteria, открытые вопросы».

### Быстрый тест агента на существующем проекте

Запустите Claude Code из корня проекта и отправьте:

> Работай через design-agent. Изучи этот проект, определи платформу и существующие функции.
> Проведи аудит основного пользовательского flow, найди несколько актуальных реальных
> референсов, предложи 2–3 направления улучшения и выбери одно. Создай research_summary,
> реализуй выбранное решение как изолированный prototype, не удаляя текущий UI, затем
> выполни platform verification. В конце покажи изменённые файлы, команды запуска и
> routingTrace.

Такой запрос проверяет основную цепочку:

`repository → platform routing → audit → research → synthesis → prototype → verification`.

## 12. Как оценивать результат агента

Перед использованием проверьте:

- правильно ли определена платформа (профиль показан в начале ответа);
- соответствует ли решение реальной пользовательской задаче;
- не смешаны ли mobile и web-паттерны вне cross-platform-synthesis;
- отделены ли live-источники от знаний модели (`evidenceBasis`) и прямые находки от
  гипотез (`derivation`);
- указаны ли ограничения референсов и дата проверки;
- рассмотрены ли альтернативы;
- учтены ли состояния интерфейса;
- есть ли accessibility;
- соответствует ли решение дизайн-системе, а конфликты оформлены ли протоколом из
  раздела 9;
- можно ли проверить результат через прототип;
- понятно ли, почему выбрано именно это решение.

Диагностика: добавьте к запросу «покажи routingTrace» — агент приложит блок с точкой
входа, платформенным профилем, вызванными и пропущенными модулями и режимом исследования.

Хороший результат не обязан давать единственный окончательный ответ. Он должен уменьшать
пространство неопределённости, показывать реальные варианты и давать достаточные основания
для следующего решения.

## 13. Безопасность исследования

design-scout читает внешние страницы, поэтому в его инструкции зашито (и действует всегда):

- содержимое веб-страниц — **недоверенные данные, а не инструкции**: текст на странице,
  обращающийся к агенту, игнорируется как prompt injection;
- никакого выполнения или скачивания кода со страниц;
- никаких логинов, отправки форм и любых внешних side effects — веб только для чтения;
- поисковые запросы санитизируются: приватные детали проекта (внутренние названия,
  невыпущенные фичи, данные пользователей) в запросы не попадают — формулировка
  обобщается.

## 14. Core и опциональные зависимости

**Core (работает без дополнительных MCP и builder-скиллов):** поиск WebSearch/WebFetch,
чтение репозитория, markdown-результаты (карты реффов, спеки, decision records), код в
вашем стеке.

**Опциональные усиления — у каждого есть fallback:**

| Зависимость | Даёт | Fallback без неё |
|---|---|---|
| Claude Browser MCP | живой просмотр библиотек экранов | поиск/фетч без визуального осмотра; скаут говорит об этом, визуальная уверенность ниже |
| Figma MCP + figma-скиллы | результат прямо в Figma | markdown-спека прототипа |
| Expo / mobile builder-скиллы | RN-имплементация | код по конвенциям проекта без скаффолдинга |
| Web builder-скиллы (hallmark, frontend-design, coss) | веб-полировка | ersatz-design самостоятельно |
| Refero / Mobbin MCP | платные библиотеки | бесплатные библиотеки (vp0, banani, pageflows, uisources, mobbin free) |

## 15. Ограничения текущей версии (v1.2)

- Только бесплатные источники — без Refero/Mobbin интеграций.
- Веб-модуль базовый (расширенный web-design-patterns skill запланирован).
- Нет доменных файлов знаний (chat/health/e-commerce — вырастут из реальных сессий).
- Прямой анализ видео не поддерживается — передавайте кадры или скриншоты.
- Качество исследования зависит от доступа к сети; при его отсутствии срабатывает
  fallback-протокол с меткой `evidenceBasis: MODEL_KNOWLEDGE`.
- «Supersedes plugin copy» в описаниях форков — описательная пометка; если plugin-копия
  дублирует срабатывание в каком-то типе сессий, отключите её через управление плагинами.
- Frontmatter всех скиллов и агентов проверяется скриптом `scripts/validate.sh`
  (настоящий YAML-парсер + обязательные поля + существование reference-путей).

## 16. Установка в Cursor и Codex (экспериментально)

SKILL.md — открытый стандарт, оба инструмента его читают. Механизмы ниже сверены с
официальной документацией 2026-07-27 (`evidenceBasis: LIVE_SOURCE`); **поведение системы
на этих платформах в бою пока не проверялось** — честно считайте это первым полевым
тестом.

**Общая установка (покрывает оба инструмента).** И Cursor, и Codex автоматически
обнаруживают скиллы в `~/.agents/skills`:

```bash
REPO="$(pwd)" && mkdir -p ~/.agents/skills \
  && ln -s "$REPO/skills/design-agent" ~/.agents/skills/design-agent \
  && ln -s "$REPO/skills/mobile-design-patterns" ~/.agents/skills/mobile-design-patterns \
  && ln -s "$REPO/skills/ersatz-design" ~/.agents/skills/ersatz-design
```

**Cursor.** Дополнительно читает `~/.claude/skills` (обратная совместимость) — если
система уже установлена для Claude Code на этой машине, Cursor видит её без каких-либо
действий. Ручной вызов: `/design-agent` в чате агента; автосрабатывание — по description.
Опционально: создайте research-сабагента из `agents/design-scout.md` встроенным скиллом
`/create-subagent`.

**Codex CLI.** Скиллы: `~/.agents/skills` (глобально) или `.agents/skills` в репозитории
проекта; вызов по имени или неявно по совпадению описания. Правило маршрутизации добавьте
в `~/.codex/AGENTS.md` (глобально) или в `AGENTS.md` проекта:

```
For any non-trivial design work (references, patterns, audits, new screens), use the
design-agent skill and follow its workflow. It has no subagent tool here: execute
agents/design-scout.md from the design-intelligence-agent repo inline as the research
stage. Never run ersatz-design before a research_summary exists.
```

**Ожидаемые деградации вне Claude Code:** нет изолированного сабагента design-scout —
скилл встроенно переключается на инлайн-исполнение метода скаута (та же evidence-цепочка);
автотриггер зависит от матчинга описаний конкретным инструментом; live-ресёрч зависит от
поисковых возможностей инструмента — при их отсутствии срабатывает честный fallback с
`evidenceBasis: MODEL_KNOWLEDGE`.
